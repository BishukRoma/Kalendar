# Kalendar — Plan razvitiya (Roadmap)

> MVP scope · Microservice architecture · Event-driven
> Дата: 2026-07-01
> Обновлено: 2026-07-01 — добавлены инсайты из Notion RealtyCalendar

---

## Архитектурный стек

### Backend (микросервисы)
- **Runtime**: Node.js (Fastify) / Go для критичных сервисов высокой нагрузки
- **Event Bus**: Apache Kafka — для всех событий бронирования
- **API Gateway**: Kong или самописный на Fastify
- **БД**: PostgreSQL (транзакционные данные), Redis (кеш, distributed locks), ClickHouse (аналитика)
- **Очереди задач**: BullMQ (iCal polling, уведомления)
- **Контейнеризация**: Docker + Docker Compose → Kubernetes (при масштабировании)

### Frontend
- **Framework**: Next.js 14 (App Router)
- **UI**: shadcn/ui + Tailwind CSS
- **State**: Zustand / TanStack Query
- **Calendar**: кастомный компонент на CSS Grid (шахматка)

### Инфраструктура
- CI/CD: GitHub Actions
- Monitoring: Grafana + Prometheus
- Logs: Loki

## Микросервисы

```
┌─────────────────────────────────────────────────────────┐
│                     API Gateway                          │
│              (auth, rate limiting, routing)              │
└──────────────────────┬──────────────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   ┌────▼───┐   ┌──────▼──┐   ┌──────▼──┐
   │Property│   │Booking  │   │Channel  │
   │Service │   │Service  │   │Service  │
   └────────┘   └─────────┘   └─────────┘
                       │
              ┌────────▼────────┐
              │   Kafka Bus     │
              │  (booking.*     │
              │   channel.*     │
              │   billing.*)    │
              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   ┌────▼───┐   ┌──────▼──┐   ┌──────▼──┐
   │Billing │   │Analytics│   │Notif.   │
   │Service │   │Service  │   │Service  │
   └────────┘   └─────────┘   └─────────┘
```

### Ключевые паттерны
- **Distributed lock (Redis)**: при получении брони с любого канала — мгновенная блокировка дат до завершения записи
- **Outbox pattern**: запись события в БД атомарно с бизнес-данными, затем relay в Kafka
- **Idempotency keys**: каждое событие бронирования имеет уникальный ключ — защита от дублей при ретраях

## Блок 4: Интеграция с каналами бронирования + Антиовербукинг

**Описание**: Самый критичный блок. Получение броней с внешних площадок и мгновенная блокировка дат на всех остальных.

**Токены (оценка)**: ~250k (включая все каналы и систему блокировок)

**Фаза**: 2

### Архитектура антиовербукинга

```
Канал получает бронь
        │
        ▼
Channel Service → Kafka topic: channel.booking.received
        │
        ▼
Booking Service:
  1. Redis SETNX lock(property_id, date_range) → если занято — reject
  2. INSERT booking (status=pending) + outbox event
  3. Рассылка в Kafka: booking.created
        │
        ▼
Channel Service:
  - Блокировка дат на ВСЕХ других каналах (iCal update + API calls)
  - Timeout 10 секунд на полный цикл блокировки
        │
        ▼
  booking.status = confirmed
```

### Каналы (P1)

#### 4.1 iCal универсальный (Airbnb, любые)
- Polling каждые 15 минут (BullMQ scheduler)
- Парсинг VEVENT из .ics файла
- Экспорт нашего iCal для подключения к площадке
- Логи синхронизации с последним статусом
- **Токены**: ~60k

#### 4.2 Ostrovok
- REST API (нужен договор + API ключ)
- Webhook для входящих броней
- Push обновлений доступности и цен
- **Токены**: ~70k

#### 4.3 Avito
- API Avito Недвижимость
- Webhook входящих броней
- Управление объявлениями через API
- **Токены**: ~60k

#### 4.4 CIAN
- API CIAN
- Синхронизация через фид или API
- **Токены**: ~60k

#### 4.5 Яндекс Путешествия
- XML-фид / API
- **Токены**: ~60k

### User Stories
- Как управляющий, я хочу подключить объект к Airbnb по iCal-ссылке, чтобы брони приходили автоматически
- Как управляющий, я хочу чтобы при получении брони с Airbnb даты немедленно закрылись на Ostrovok и Avito
- Как управляющий, я хочу видеть лог синхронизации с каждым каналом (последний статус, ошибки, время)

## Ключевые инсайты из Notion RealtyCalendar

### Механика создания брони (шахматка)
RC использует паттерн `preparing=true`: при открытии попапа сразу создаётся черновик брони без валидаций, получается ID. Пользователь настраивает детали, по «Сохранить» — финальные валидации. **Наш вариант**: аналогично, через Kafka `booking.draft.created` → `booking.confirmed`.

### Залог (deposit) — правила
- Только один залог на бронь (кнопка «добавить» скрывается)
- Залог нельзя редактировать после создания
- Возврат: сумма + штраф = полная сумма залога
- Комиссию Монеты за залог перекладывают на гостя — гость видит: «залог будет возвращён при соблюдении условий»

### Channel Manager — 4 типа подключений (строить сразу правильно)
1. **iCal** — только занятость, раз в час. Наш редис-лок всё равно нужен поверх.
2. **Один экран** — ID + наценка + валюта. Большинство мелких площадок.
3. **По шагам** — отель → категория → тарифы (Booking, Ostrovok, Expedia…)
4. **Аккаунт+объекты** — Avito (письмо → client_id/secret), Airbnb (пока iCal)

### iCal — критическое ограничение
Синхронизация **раз в час**, только занятость, **без цен**. Это главная причина овербукинга у RC. Наше решение: Redis distributed lock при любой брони блокирует даты мгновенно независимо от канала.

### MiniCRM — модуль для горничных (Блок 10, пост-MVP)
- Гостевая ссылка: даты, оплаты, карта, описание, доп. услуги, код ключницы
- Единая доска менеджера: заезды сегодня/завтра, долги, уборки
- Telegram-бот для горничных: уведомления о выезде → можно ехать убираться
- Расходы на уборку → автоматически в расходы объекта

## Решения по стеку (фиксация)

| Решение | Выбор | Причина |
|---|---|---|
| Event bus | Kafka | Высокий throughput, retention, replay |
| Lock | Redis SETNX | Мгновенная distributed блокировка |
| OLTP DB | PostgreSQL | Надёжность, JSON поддержка |
| Analytics DB | ClickHouse | Быстрые аналитические запросы |
| Task queue | BullMQ (Redis) | iCal polling, уведомления |
| Frontend | Next.js 14 | SSR, App Router, производительность |
| Auth | JWT + refresh | Stateless, просто масштабируется |
| Container | Docker | Стандарт, просто локально и в prod |
